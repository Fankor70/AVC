# YummyAnime Real-Site Account Integration, Persistent Session, User Data Synchronization, and Low-Overhead Live Updates

You are working on an existing Windows desktop application called **Anime Voice Control**.

The application is a C# / .NET 8 / WPF application using MVVM and WebView2.

The application currently embeds YummyAnime and provides voice control, playback control, tabs, search, episode navigation, fullscreen, autoplay, watch history, and other functionality.

I now need a production-quality integration with the **real YummyAnime website**.

The key requirement is:

> The application must use the REAL YummyAnime website and the user's REAL YummyAnime account/session.

Do NOT create a fake local authentication system.

Do NOT create a fake local representation of the account as the source of truth.

Do NOT invent an undocumented YummyAnime API.

The real website must remain the source of truth whenever the website provides the required information.

---

# 1. PRIMARY OBJECTIVE

Implement a complete account integration layer that allows the user to:

1. Open YummyAnime inside the application.
2. Log into YummyAnime normally through the real website.
3. Keep the authenticated session between application launches.
4. Detect whether the user is currently logged in.
5. Read user-visible account information from the authenticated website.
6. Read the user's:

   * username / display name
   * avatar
   * watch history
   * watched episodes
   * watch progress when available
   * bookmarks / favorites
   * saved anime
   * profile information that is actually exposed by the website
7. Keep the application's UI synchronized with the real website.
8. Detect relevant changes made on the website.
9. Update the application without constantly hammering the website.
10. Keep synchronization lightweight and asynchronous.
11. Avoid unnecessary network requests.
12. Preserve the real website's authentication/session behavior.

---

* bypass CAPTCHA

* impersonate another client

# 13. SYNCHRONIZATION TRIGGERS

Synchronize when one of these events occurs:

### A. Application startup

Perform one initial synchronization.

Priority:

```text
Authentication
↓
Profile
↓
Bookmarks
↓
Recent watch history
```

Do not block application startup while waiting for every request.

The UI should become usable immediately.

Show cached information first when available.

Then update it asynchronously.

---

### B. Successful login

Immediately perform:

```text
Full account synchronization
```

because the application may previously have been logged out.

---

### C. User opens account page

Refresh account data if the cache is stale.

---

### D. User opens bookmarks

Refresh bookmarks if stale.

Do not refresh bookmarks every second.

---

### E. User opens history

Refresh watch history if stale.

---

### F. User starts watching an episode

Do not immediately download the entire history.

Instead:

```text
Update current episode state
```

and synchronize the relevant item.

---

### G. Episode finishes

Immediately attempt to synchronize the relevant watch state.

---

### H. Bookmark changed

After a bookmark/favorite action:

```text
perform action
↓
wait for website confirmation
↓
refresh affected bookmark state
```

Do not reload the entire account.

---

### I. Website navigation

If navigation changes to:

```text
/profile
/history
/bookmarks
/anime/...
/episode/...
```

the adapter may trigger a targeted synchronization.

# 16. NETWORK-AWARE SYNCHRONIZATION

Use:

```csharp
CancellationToken
SemaphoreSlim
Debounce
Throttle
Retry with backoff
```

Prevent duplicate simultaneous sync operations.

Example:

```text
5 events happen in 500 ms

Do NOT execute:

Sync()
Sync()
Sync()
Sync()
Sync()
```

Instead:

```text
events
 ↓
debounce
 ↓
one synchronization request
```

# 17. CONCURRENT SYNCHRONIZATION CONTROL

Only one synchronization of a particular resource should run at a time.

For example:

```text

ProfileSync
```

can have independent locks.

But:

```text

Bookmark timer expired
```

# 18. NETWORK REQUEST MONITORING

WebView2 provides APIs for observing web resource requests and responses.

Use this capability carefully and only where it genuinely improves synchronization.

Do not capture every network request.

Do not log:

* passwords
* authentication headers
* access tokens
* refresh tokens
* session cookies
* sensitive personal data

Filter requests narrowly to relevant YummyAnime resources.

Possible useful categories:

```text
profile
bookmarks
history
watch state
anime metadata
```

If the site has legitimate JSON/XHR requests used by the page itself, inspect and document them.

Do not invent endpoints.

Do not blindly intercept all network traffic.

Microsoft documents WebView2's WebResourceRequested/WebResourceResponseReceived mechanisms for monitoring and modifying web requests, but recommends using simpler APIs where possible.

# 23. CHANGE DETECTION

Every synchronized resource should have a fingerprint/hash/version where practical.

Example:

```text
Bookmarks:
hash(bookmark IDs)

History:
hash(relevant episode IDs + watched states)

Profile:
hash(username + avatar URL)
```

If:

```text
newHash == oldHash
```

do nothing.

If:

```text
newHash != oldHash
```

update the local cache and notify the UI.

This prevents unnecessary UI updates.

```text

```

```text

```

For example:

```text

 ↓

```

If the change happens externally outside the application:

```text

 ↓

```

Use smart refresh triggers rather than 1-second polling.

# 52. IMPORTANT WEBVIEW2 RULE

Do not build an authentication system around extracting cookies/tokens from WebView2.

Use the persistent browser profile for the normal website session.

Microsoft explicitly documents persistent WebView2 profile data for maintaining sign-in across launches, while warning against scraping authentication tokens from redirects/navigation/cookies for OAuth-style flows.

If YummyAnime uses a special external OAuth provider rather than ordinary site login, inspect that flow first and implement the provider's supported desktop authentication mechanism instead of scraping tokens.
