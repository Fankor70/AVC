# PRODUCTION FIX & ADVANCED PLAYER CONTROL

## Anime Voice Controller — Player, Autoplay, Fullscreen, Skip Buttons, Voice Control and Self-Diagnostics

You are modifying an existing Windows 10 desktop application built with C#/.NET/WPF + WebView2.

The application is a voice-controlled anime browser/player designed for couch/TV-style usage.

DO NOT rewrite the entire application from scratch.

First inspect the existing architecture and implementation, identify the current player-control, voice-command, WebView2, fullscreen, tab, and site-adapter systems, then improve them while preserving working functionality.

The main goal of this task is:

> Make the application capable of reliably controlling the entire anime website and video player through voice commands with minimal latency, while automatically detecting failures and recovering from them.

The application must not assume that the website will always behave identically.

# 1. CURRENT PROBLEMS TO FIX

The following problems currently exist and must be investigated and fixed.

## Problem A — Episode opens but video does not start automatically

When a new episode is opened, the video player sometimes appears in a paused state with a large Play button in the center.

The user currently has to manually click the Play button.

The application must support:

Voice command:

"Play"

"Start"

"Start video"

"Continue"

"Play episode"

"Включи"

"Запусти"

"Продолжить"

"Включи серию"

The application must:

1. Detect the actual video element.
2. Detect whether it is paused.
3. Detect whether the video has enough media loaded.
4. Attempt playback.
5. Verify that playback actually started.
6. Report failure if playback did not start.
7. Retry using an appropriate fallback.
8. Never report "success" if the video is still paused.

Do NOT simply execute:

video.play();

and assume success.

Use the Promise returned by HTMLMediaElement.play() and verify the resulting state.

Possible states:

* playing
* paused
* loading
* buffering
* ended
* blocked
* unavailable
* unknown

The application must expose these states internally.

# 4. SMART PLAY COMMAND

Create:

```text
PlayVideo()
```

It must work approximately like this:

```text
1. Find active video/player
2. Check current state
3. If already playing:
       return SUCCESS
4. If paused:
       attempt play()
5. Wait for confirmation
6. If playing event occurs:
       SUCCESS
7. If play() fails:
       diagnose failure
8. Try fallback
9. Verify again
10. If still failed:
       report exact failure
```

Possible failures:

```text
AUTOPLAY_BLOCKED
VIDEO_NOT_READY
VIDEO_NOT_FOUND
PLAYER_NOT_FOUND
MEDIA_ERROR
PLAYER_UI_BLOCKING
SITE_CHANGED
UNKNOWN
```

Do not hide these failures from diagnostics.
